Skills are custom instruction sets you can give me to specialize my behavior for specific tasks. Here's how to create one:

## Creating a Skill

**1. Pick a location:**
- **Project-level** (shared with your team): `.bob/skills/<skill-name>/SKILL.md` inside your project root
- **Global** (available in all projects): `~/.bob/skills/<skill-name>/SKILL.md`

**2. Create a `SKILL.md` file** with YAML front matter + instructions:

```markdown
---
name: code-review
description: Review code for bugs, security issues, and best practices
---

When reviewing code, check for:
- Security vulnerabilities
- Performance issues
- Missing error handling at API boundaries

Provide a summary with severity levels for each finding.
```

**Required fields:**
- `name` — display name used in the Bob interface
- `description` — helps me decide when to activate the skill automatically; skills without a description are ignored

## How Skills Work

- Everything **below** the `---` delimiter becomes the instructions I receive when the skill is activated
- Skills load **once per conversation** to avoid duplicate prompts
- I automatically decide when to activate a skill based on the description matching your request
- You can also include **supporting files** (checklists, templates, scripts, etc.) alongside `SKILL.md` in the same folder — I can read them once the skill is activated

```
your-project/
└── .bob/
    └── skills/
        └── my-skill/
            ├── SKILL.md
            ├── checklist.md
            └── style-guide.md
```

# CNTRL F

### *Find your way through any codebase.*

**CNTRL F** is an AI-powered web application that helps developers understand unfamiliar GitHub repositories by turning the codebase into an **interactive visual map** and providing a **codebase-aware AI assistant**.

Instead of spending hours searching through files and trying to understand how everything connects, a developer can paste a GitHub URL and immediately explore the project's architecture.

---

## 🎯 The Problem

When developers join an unfamiliar project, one of the hardest parts isn't writing code—it's **figuring out where everything is**.

You might ask:

> "Where is authentication handled?"

> "What does this function actually affect?"

> "Where should I add this feature?"

> "Why does this file depend on that one?"

Normally, answering these questions means searching through hundreds or thousands of files.

---

## 💡 The Solution

The user simply enters:

```text
https://github.com/example/project
```

CNTRL F then:

```text
GitHub Repository
       ↓
Repository Analyzer
       ↓
Code Structure + Dependencies
       ↓
Interactive Codebase Graph
       ↓
AI-powered exploration
```

The user can visually navigate the codebase and ask questions about it.

# 🕸️ 1. Interactive Codebase Graph

This is the **signature feature**.

Instead of showing the repository as a boring file tree, CNTRL F creates an interactive graph similar in spirit to **Obsidian's Graph View**.

For example:

```text
             ┌──────────────┐
             │   App.tsx    │
             └──────┬───────┘
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
   ┌────────────┐      ┌─────────────┐
   │ Auth.tsx   │      │ Dashboard   │
   └─────┬──────┘      └──────┬──────┘
         │                    │
         ↓                    ↓
   ┌────────────┐      ┌─────────────┐
   │ Auth API   │─────→│ UserService │
   └────────────┘      └─────────────┘
```

Users can:

- zoom and pan
- click files/components
- see relationships
- inspect files
- search for specific components
- highlight connected parts of the application

We **don't want to display every function and file simultaneously**, because that would become an unreadable hairball.

Instead, the graph starts at the architecture/module level and lets users drill down.

---

# 💬 2. Codebase-Aware AI

CNTRL F has an AI assistant, but it isn't supposed to be a generic chatbot.

It knows about the repository being explored.

For example:

**User:**

> Where is authentication handled?

**CNTRL F:**

> Authentication is primarily handled through `AuthService.ts` and `auth.routes.ts`. The frontend communicates with the authentication API through `api/auth.ts`.

It could also answer:

> What does this function do?

> Where is this function used?

> Where should I add Google authentication?

> How does data get from the frontend to the database?

> Why does this file depend on that one?

The important part is that the AI answers using the **actual repository structure and source code**.

---

# 🔥 3. Impact Explorer

This is another major feature.

The user selects a file or component and CNTRL F determines what depends on it.

For example:

```text
UserService.ts
      ↓
 ┌────┴─────┐
 ↓          ↓
Auth.ts   Profile.ts
 ↓          ↓
Login UI   Profile UI
```

CNTRL F can then explain:

> Changing `UserService.ts` may affect authentication and profile functionality. Review `Auth.ts`, `Profile.ts`, and their associated tests.

The important design principle is:

**Static analysis determines the actual relationships. AI explains them.**

This helps reduce AI hallucinations.

---

# 🧭 4. Guided Onboarding

CNTRL F can also help someone **learn an unfamiliar repository**.

Instead of randomly clicking around, the AI generates an onboarding path such as:

```text

        ↓
3. Understand authentication
        ↓
4. Explore the API
        ↓

        ↓

```

Clicking a step can highlight the relevant parts of the graph.

So CNTRL F isn't just:

> "Here's an AI that answers questions."

It's more like:

> **"Here's a map of the software, and I'll help you navigate it."**

**Go full TypeScript stack** — React + Vite frontend, Node.js backend (Express or Hono).

- One language, less context switching under time pressure
- Parsing JS/TS imports is easier *in* JS/TS
- No Python environment setup, no CORS headaches between two dev servers
- You can even start with everything in the frontend and extract to a backend later

The only reason to pick Python is if the hackathon's AI API has a Python-only SDK — worth checking.

## What is a Skill?

A skill is a `SKILL.md` file that gives me specialized instructions for a specific, recurring task. When you make a request that matches a skill's description, I automatically load its instructions and follow them.

---

## File Structure

```
.bob/skills/<skill-name>/SKILL.md
```

- **Workspace skill** (this project only): `.bob/skills/<skill-name>/SKILL.md`
- **Global skill** (all projects): `~/.bob/skills/<skill-name>/SKILL.md` (i.e. `C:\Users\Jeb\.bob\skills\`)

---

## The SKILL.md Format

```markdown
---
name: my-skill
description: Use when the user wants to do X — walks through steps A, B, and C.
---

# My Skill

Follow these steps when activated:

1. Do this first...
2. Then do this...
3. Finally, do this...
```

**Required frontmatter fields:**

| Field | Purpose |
|---|---|
| `name` | Must match the folder name exactly |
| `description` | **The trigger** — drives auto-activation. Write it as "Use when the user wants to…" |

---

## Name Rules ⚠️

The directory name (= skill name) must match:
```
lowercase letters, digits, single dashes only
```
✅ `code-review`, `api-docs`, `my-skill2`  
❌ `Code_Review`, `my skill`, `--bad`, `MySkill`

An invalid name causes the skill to be **silently skipped** with no error.

---

## Optional: Advanced Metadata

Only add this if you need to change default behavior:

```markdown
---
name: my-skill
description: Use when...
metadata:
  disable-model-invocation: true  # Only runs when user types /my-skill, no auto-activation
  argument-hint: "[filename]"     # Hint shown in autocomplete after /my-skill
---
```
